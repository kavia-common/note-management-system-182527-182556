# Notes Database Documentation

This folder documents the persistence choice, data schema, and initialization guidance for the Notes application backend.

## Persistence Choice (MVP)

For the MVP, we choose a JSON file store using a lightweight adapter (e.g., `lowdb` or a comparable JSON file store). This choice provides:
- Zero external dependencies (no DB server required)
- Simplicity for local development and CI
- Easy inspection and manual editing during early iterations

The design abstracts persistence behind a backend adapter interface, so we can swap to SQLite or another DB later without changing the frontend or business logic.

## Data Location

- Environment variable driven path (do not hardcode in code):
  - JSON store path from env: `NOTES_DB_JSON_PATH`
- Recommended default path in development (if env is not set):
  - `./data/notes.json` (relative to backend service root)

Important: The backend code must read the path from the environment. The `.env` file will be managed by the orchestrator. Do not commit real secrets or environment-specific values to the repo.

You may create a `.env.example` with:
```
# Example environment variables for the Notes backend
NOTES_DB_JSON_PATH=./data/notes.json
# If you later use SQLite:
NOTES_DB_SQLITE_PATH=./data/notes.sqlite
```

## JSON File Structure

Single-file JSON database with a top-level object:
```json
{
  "notes": [
    {
      "id": "n_1719943680123_x8c2",
      "title": "Untitled",
      "content": "",
      "pinned": false,
      "updatedAt": "2025-01-01T10:20:30.000Z"
    }
  ]
}
```

- The file must always contain a `"notes"` array (empty array is valid).
- Backend is responsible for ensuring atomic writes and basic integrity.

## Note Schema

A Note object has the following fields:

- id (string): Unique identifier. Generated by backend.
- title (string): Note title. May be empty string.
- content (string): Note content, markdown/plain text allowed.
- pinned (boolean): Whether the note is pinned. Default: false.
- updatedAt (string, ISO 8601): Last updated timestamp set by backend.

TypeScript-like schema:
```ts
type Note = {
  id: string;          // e.g., "n_1719943680123_x8c2"
  title: string;       // non-null, can be ""
  content: string;     // non-null, can be ""
  pinned: boolean;     // default false
  updatedAt: string;   // ISO 8601 string
};
```

Validation Rules:
- id: non-empty, unique
- title: string (trim optional on backend)
- content: string
- pinned: boolean
- updatedAt: valid ISO string; set by backend when creating/updating/pinning

## Backend Adapter Interface Compatibility

The frontend calls the backend REST API through these routes (as implemented/expected by the frontend service layer):

- GET `/notes` → returns `Note[]`
- GET `/notes/search?q=...` → returns `Note[]` filtered by title/content
- POST `/notes` with `{ title, content, pinned? }` → returns created `Note`
- PUT `/notes/:id` with partial `{ title?, content?, pinned?, updatedAt? }` → returns updated `Note`
- DELETE `/notes/:id` → returns 204/200
- POST `/notes/:id/pin` → toggles pin, returns updated `Note` (idempotent behavior acceptable)

The persistence adapter should expose methods like:
- listNotes(): Promise<Note[]>
- searchNotes(query: string): Promise<Note[]>
- createNote(input: { title: string; content: string; pinned?: boolean }): Promise<Note>
- updateNote(id: string, patch: Partial<Note>): Promise<Note>
- deleteNote(id: string): Promise<void>
- togglePin(id: string): Promise<Note>

This interface is deliberately simple and maps 1:1 to the routes.

## Initialization & Seed Guidance (JSON)

1) Ensure data directory exists:
   - Create `./data` (or a configured directory) if missing.

2) Create initial `notes.json` if missing:
```json
{
  "notes": []
}
```

3) Optional seed content (dev only):
```json
{
  "notes": [
    {
      "id": "seed_1",
      "title": "Welcome to Ocean Notes",
      "content": "This is your first note! Edit me to get started.",
      "pinned": true,
      "updatedAt": "2025-01-01T12:00:00.000Z"
    },
    {
      "id": "seed_2",
      "title": "Keyboard Tips",
      "content": "- Start typing to autosave\n- Use search to filter notes",
      "pinned": false,
      "updatedAt": "2025-01-01T12:05:00.000Z"
    }
  ]
}
```

4) Concurrency/Write Safety:
   - Use a library that performs atomic writes (e.g., `lowdb` with file adapter or similar).
   - For multi-process environments, move to SQLite or a proper DB.

## Migration Path to SQLite (Optional)

While not required for MVP, a SQLite backend offers stronger guarantees for concurrency and indexing. If/when switching:

- Read DB path from env: `NOTES_DB_SQLITE_PATH`
- Use the schema below to initialize the database
- Provide a migration script to move data from JSON to SQLite

See `schema.sql` in this folder for table definitions and indexes.

## Operational Considerations

- Backups: For JSON, periodically copy the file (ensure process is not writing at that moment).
- Data size: JSON is best for small datasets. If notes count grows large (e.g., >10k), move to SQLite/Postgres for performance and search.
- Search: For JSON MVP, simple in-memory filtering is acceptable. SQLite provides LIKE/FULL-TEXT options later.
